# Протокол сбора данных: Кровные узы и Сад

## Зачем это нужно

Цель — получить таблицы, которые можно использовать в точном планировании аккаунта, а не коллекцию похожих чисел. Отдельная строка не становится расчётным фактом только потому, что она выглядит правдоподобно или совпала с другим сторонним калькулятором.

В репозитории различаем четыре состояния:

- `candidate` — число из открытого сообщества или старой таблицы.
- `observation-only` — число переписано с конкретного экрана, но его значение для формулы или перехода ещё не установлено.
- `verified-in-game` — строка сверена в актуальном клиенте, смысл поля и перехода известен.
- `conflict` — источники противоречат друг другу или экран нельзя однозначно сопоставить с таблицей.

Только строки со статусом `verified-in-game` допускаются к новым планировщикам. Догадки, интерполяция и автоматическое округление не повышают статус строки.

## Общие поля для любого числового значения

Каждая принятая запись должна сохранять:

| Поле | Содержание |
|---|---|
| `sourceId` | Ссылка на источник в `game-data/source-manifest.json` или ID игрового наблюдения |
| `evidenceType` | `in-game-screenshot`, `in-game-before-after`, `official-notice`, `community-table` или `workbook` |
| `capturedAt` | Дата получения факта |
| `gameVersion` | Версия клиента, если её можно установить |
| `screen` | Точное название экрана и блока |
| `status` | Один из статусов выше |
| `rawDisplay` | Неизменённый текст, показанный игрой |
| `normalizedValue` | Числовое значение только после установления единиц измерения и смысла поля |
| `notes` | Что именно было проверено и что осталось неизвестным |

Сокращение вроде `936.12K` можно нормализовать в `936120`, но нормализованное число всё ещё означает только то поле, которое действительно показано на экране. Не следует объявлять его приростом господства, если экран показывает атрибут или процентный бонус.

## Кровные узы — одна строка на каждый уровень каждого навыка

Минимальная структура записи:

| Поле | Требование |
|---|---|
| `warden` | Точное локализованное имя Смотрителя из текущей игры |
| `partner` | Точное имя партнёра; нельзя выводить перевод из похожего английского имени |
| `skillName` | Точное имя навыка |
| `level` | Уровень, к которому относится значение строки |
| `metric` | Явный тип значения: например, `flat-attribute` или `percentage`; нельзя складывать их как одну величину |
| `value` | Числовое значение этого же навыка на этом уровне |
| `upgradeCost` | Цена перехода с предыдущего уровня на уровень этой строки. Если экран показывает цену следующего перехода, она должна быть сохранена отдельно и не переназначаться молча |
| `evidence` | Источник, версия, экран и статус проверки |

Для планирования с уровня 131 до 135 нужны непрерывные строки 131, 132, 133, 134 и 135. Нельзя восстанавливать 132–134 по формуле, выведенной из крайних уровней. Нельзя сравнивать процент с плоским приростом атрибута.

В текущем движке `bloodBondProgressionPlan` возвращает расчёт только если у каждого нужного уровня есть подтверждённые строки с одним и тем же типом метрики, числовым значением и ценой перехода. Он не преобразует процент в господство автоматически. Для последнего нужна отдельная подтверждённая связь с формулой атрибутов и бонусами конкретного Смотрителя.

## Сад — одна строка на каждый уровень эффекта

Минимальная структура:

| Поле | Требование |
|---|---|
| `level` | Уровень эффекта |
| `category` | Подтверждённая применимость: `single`, `dual` или `universal` |
| `effects` | Список атрибутов и прибавок, строго разложенный по четырём атрибутам |
| `cost` | Цена именно перехода с предыдущего уровня на этот уровень |
| `evidence` | Скриншот/источник, дата и версия |
| `status` | Статус подтверждения |

Для планирования всего аккаунта нужен также проверенный состав Смотрителей по категории и сильным атрибутам: сколько подходящих Смотрителей реально получает каждый бонус. Одного числа «всего открыто Смотрителей» недостаточно для избирательного эффекта, который увеличивает только Силу, Харизму, Интеллект или Волю у конкретной категории.

Планировщик `gardenAttributePlan` возвращает стоимость и прибавки атрибутов только при непрерывной таблице и подтверждённых количествах Смотрителей по паре «категория × сильный атрибут». Его результат — прибавки атрибутов, а не финальное господство аккаунта. Преобразование в господство должно идти через подтверждённую модель атрибутов соответствующего Смотрителя, Вдохновения, талантов, книг, Кровных уз, Конклава и других эффектов.

## Контрольная сверка до включения строки

1. Записать текущее отображение и цену перехода.
2. Зафиксировать исходные атрибуты соответствующего Смотрителя и господство аккаунта, если эти значения доступны.
3. Выполнить одно улучшение без параллельной прокачки других систем.
4. Снова записать атрибуты Смотрителя, эффект навыка/Сада, цену или остаток ресурса и господство.
5. Проверить, что изменение совпадает с моделью, и повторить контроль на другом Смотрителе/уровне.
6. Только после этого менять статус на `verified-in-game` и добавлять регрессионный пример.

Если обновление игры меняет экран или значения, предыдущую строку не удалять: пометить её версией, в которой она наблюдалась, и собрать новую.

- Агрегаты Конклава 180 уровней, 19 233 610 455 очков ветки, 987 000 атрибута и 1 056% книг сохраняются как утверждение источника; они не заменяют отсутствующие построчные значения старой таблицы.

## Не делать

- Не экстраполировать соседние уровни.
- Не трактовать `4280/170` как цену, пока не установлено, что обозначают обе части.
- Не считать отображаемое `+X` приростом общего господства без подтверждения.
- Не включать кандидаты из сторонних таблиц в общий итог аккаунта.
- Не менять старые формулы без сохранения прежних тестов и контрольного сравнения.
